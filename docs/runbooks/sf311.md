# 311 alarms

New 311 jobs use their own queue, worker and dead-letter queue (DLQ).
The DLQ holds jobs that used all five tries. Some failed jobs stop sooner,
so an empty DLQ does not mean all work passed. Old jobs stay in the
submissions queues.

Names start with `good-neighbor-app-<env>-`. The new resources end in
`311`, `311-worker` and `311-dlq`.

## Read the alarm

All limits below use five-minute periods.

| Alarm | What it means |
| --- | --- |
| `311-connection-failed` | At least three calls failed due to a network, timeout, access, rate limit or server error. This does not prove that all of SF311 is down. |
| `311-reconciliation-blocked` | At least one job or action stopped with an unknown ticket state or an unconfirmed write. Check what happened before trying again. |
| `311-action-failed` | At least one other job or action failed and will not retry, or used its last try. Check the reason in the logs. |
| `311-dlq-not-empty` | SQS reported at least one visible message in the DLQ. |
| `311-queue-backlog` | The oldest job is over ten minutes old in two periods in a row. Retries can affect this age. |
| `311-worker-lambda-errors` / `311-worker-lambda-throttles` | At least one worker run failed, timed out or was blocked by a limit. A job returned for retry does not count as a failed worker run. |

The first three count failure events. Their return to OK means a quiet period,
not a confirmed fix. One fault can set off more than one alarm. Counts can also
repeat or miss events. Check the saved job state; do not add chart counts to
get the number of stuck jobs.
SQS queue counts are estimates.

## Check the cause

In CloudWatch Logs Insights, select the environment's `-311-worker`, `-worker`,
`-analysis` and `-api` log groups. Use these queries to find failed actions and
calls:

```sql
fields @timestamp, Operation, reason, outcome, jobId, taskId, siteId, attempt
| fields messageId, name, awsRequestId, stack
| filter marker = "Sf311ActionFailure" or eventType = "sf311_job_error"
| sort @timestamp desc
```

```sql
fields @timestamp, Operation, category, reason, httpStatus
| filter marker = "Sf311Request" and outcome = "failed"
| sort @timestamp desc
```

Use the site and job IDs to read the saved result in DynamoDB. Use the task ID
when no job ID is logged. Keep ticket text, secrets and media links out of shared
logs or reports.

`sf311_closure_state_unknown` means the app could not find the ticket's state
in the feed. It does not prove that 311 is down or the ticket was deleted.
Check the ticket ID, feed contents and how the code reads the feed.

Use logs, metrics and database reads. **Do not poll SQS messages:** polling
changes their state. Do not resend a City request until you know if it already
took effect.

## Manual filing during training

Compliance supervisors can change **Enable 311** on each row
of the dashboard's Sites list. Checked enables real City delivery; unchecked
simulates manual filings without sending a ticket. Use **Save changes** to apply
edits, or **Discard changes** to restore saved values. Filtering preserves pending
edits, including edits to sites no longer visible.

Sites save independently through the existing version-checked, audited setting
API. Successful edits clear from the pending list; failures remain for retry.
If a site changed concurrently, review its current and requested settings before
using the latest version and saving again. An uncertain response is read back
before retrying a write.

The setting is captured when a filing is accepted. Changing it does not redirect
already-accepted filings or their retries, and does not change silent 311 filing.
A site without an explicit setting defaults to real delivery. The same setting
remains available under the site's App settings.

## Read-only reconciliation

Run the scoped report with an approved environment profile and table name:

```sh
AWS_PROFILE=<profile> AWS_REGION=us-west-2 DYNAMO_TABLE=<table> \
  node backend/scripts/report-sf311-recovery.mjs --site <site-id> --test-site <test-site-id>
```

Repeat `--site` or `--test-site` for additional sites. Test-site labels are explicit
operator inputs, not guesses based on names. The command uses paginated,
consistent DynamoDB queries only. It never reads queue messages, invokes the
classifier, sends City requests, or changes records. Each read is consistent,
but the report is not a transactional snapshot across all sites.

The report separates current-action failures from retained historical-action
failures and counts distinct tasks in each group. A task can appear in both.
Manual simulations do not clear silent failures. The report merges task results
with durable job checkpoints, so a failed final task write cannot hide an
unconfirmed City creation. It also lists job-only failures whose task is missing.
Matching confirmed ticket references supersede stale pending evidence; a newer
failed attempt alone does not establish that an older uncertain creation failed.
Partial or pending creations remain visible for reconciliation. Job status counts include historical jobs
and must not be interpreted as the number of unresolved tasks. Code-21 action
results are counted separately and excluded from the report's failure list.
Retained results are not a complete archive of attempts; a missing result does
not prove a historical filing recovered.

Historical classification failures require operator review; users cannot replace
the original photos or text to retry them. This command never replays them.
An inconclusive image classification gets one fallback using the saved description. If classification still cannot route,
graffiti uses `1.5.1.1.18.0` and bulky items use `1.1.4.7.7.0`. These are the only
two classifier commands wired into 311 routing. Empty/malformed responses,
unmapped labels, unavailable evidence and classifier errors all use the default.
Recognized labels retain specific service codes, including when another label
requires a default. Existing tickets are resumed rather than creating an extra
default ticket, and unconfirmed City creations still require reconciliation.
The complete chosen service-code list is saved in every classifier filing
checkpoint before the first City creation. Retries reuse that list without
reclassifying, including any services not yet attempted or previously rejected.
Older partially filed multi-service records without a complete saved selection
require reconciliation rather than guessing that the known tickets are all the
intended tickets.
Location, delivery-mode, City-response and attachment safeguards remain in force.

`Sf311Classification` records classifier, outcome, input type, text fallback,
label count and a bounded default reason without text, labels, images or raw
errors. Verify a real submitted ticket separately from a simulated submission.

`sf311_lease_contended` identifies a failed claim on another worker's active
lease. It keeps the existing bounded visibility delay and retries; it is not
a City connection failure. Confirm the job's saved status and checkpoints
before deciding that a retry is needed.

## Media and authorization diagnosis

`Sf311MediaAccess` records only the API request ID and a bounded `Reason`:
`missing_token`, `invalid_token`, `unknown_lease`, `invalid_lease`,
`expired_lease`, `redirected` or `internal_error`. Correlate request IDs with
API Gateway access logs. No bearer token, token hash, media key or URL is logged.
The 48-hour lease and public 404 behavior are unchanged; do not extend retention
to hide failures. A redirect or successful attachment API call does not prove
that the City retrieved and stored the image.

For ticket-endpoint 401s, first inspect `integrationStat`: `-` means no integration
status was recorded, so the failure is not evidence of a City API failure.
Compare timing with refresh responses and deployment/test activity before
attributing a burst to real users. The client already retries through session
refresh once. Queued-filing watchers stop only after an explicit reauthentication
error. Ordinary 401s can reflect a concurrent token-rotation race and retain
bounded polling retries. Returning through an authenticated view starts a new watcher.
