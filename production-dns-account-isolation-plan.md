# Production DNS Account-Isolation Plan

## Objective

Establish and preserve these environment boundaries:

- `dev.goodneighborsf.org` remains the development and test instance, with its Route 53 hosted zone, application resources, and deployment role in the DEV AWS account.
- `goodneighbor.sf.gov` becomes the production instance, with its Route 53 hosted zone, application resources, and deployment role in the PROD AWS account.

The two domains must use separate Route 53 hosted zones and separate authoritative name servers. Reusing the DEV zone's name servers for production would undermine the intended account isolation.

## Plan

### 1. Inventory the current DNS and account state

- Confirm which AWS account currently owns the `goodneighbor.sf.gov` hosted zone.
- Record its hosted-zone ID, four Route 53 name servers, DNSSEC status, DS record, and all existing DNS records.
- Confirm that `dev.goodneighborsf.org` is delegated to the DEV-account hosted zone and resolves to the DEV CloudFront distribution.
- Determine whether the `sf.gov` parent zone already contains NS or DS records for `goodneighbor.sf.gov`.
- Record current TTLs and authoritative answers so the later cutover can be verified.

### 2. Preserve development in the DEV account

- Keep the `dev.goodneighborsf.org` public hosted zone in the DEV AWS account.
- Keep its ACM certificate, CloudFront distribution, A and AAAA aliases, application resources, and Terraform state owned by DEV.
- Keep the parent `goodneighborsf.org` zone's NS delegation for `dev.goodneighborsf.org` pointed at the four name servers assigned to the DEV hosted zone.
- Do not replace or reuse those name servers for production.
- Verify that DEV CI assumes only the DEV deployment role and enforces the expected DEV account ID.

### 3. Create or adopt the production zone in the PROD account

- Run the production DNS provisioning workflow through the PROD GitHub Environment, using the PROD deployment role.
- Enforce the expected PROD account ID during AWS credential setup.
- Create `goodneighbor.sf.gov` as a Route 53 public hosted zone in PROD, unless an appropriate PROD-owned zone already exists and is adopted into Terraform state.
- Capture the four authoritative name servers assigned to the PROD zone. They are expected to differ from the DEV hosted zone and from any earlier DEV-owned `goodneighbor.sf.gov` zone.
- Create the production DNSSEC KMS key, Route 53 key-signing key, hosted-zone signing configuration, encrypted query logging, and required log-resource policy in PROD.
- Protect the production hosted zone and signing key from accidental destruction.

The repository already models this direction: the production DNS workflow is restricted to PROD account `701893741736`, and the production Terraform root declares the `goodneighbor.sf.gov` zone and its DNSSEC resources.

### 4. Populate and validate the PROD zone before delegation

- Create the DNS validation records for the production ACM certificate in the PROD zone.
- Issue the production certificate in `us-east-1`, as required by CloudFront.
- Configure the PROD CloudFront distribution with `goodneighbor.sf.gov` as an alias and attach the production certificate.
- Create apex A and AAAA Route 53 alias records pointing to the PROD CloudFront distribution.
- Add any other required production DNS records, reviewing each target rather than copying DEV-specific records blindly.
- Confirm that every production DNS target references the intended PROD resources.
- Where possible, test the new distribution and certificate before public delegation, including direct CloudFront checks and controlled DNS resolution.

### 5. Change the parent `sf.gov` delegation through DT

- Give DT all four name servers generated by the PROD-account `goodneighbor.sf.gov` hosted zone.
- Ask DT to create or replace the `goodneighbor.sf.gov` NS delegation in the parent `sf.gov` zone.
- If an earlier DEV-owned production zone is already delegated, treat this as an NS replacement; Route 53 cannot move a hosted zone between accounts or preserve its assigned name-server set.
- Coordinate lower migration TTLs in advance if DT policy permits. Existing TTLs cannot be shortened retroactively once cached, so allow at least the previous TTL before relying on the cutover.

### 6. Establish the DNSSEC chain of trust in the correct order

- Enable DNSSEC signing on the PROD hosted zone and confirm that its signing status is healthy.
- Complete the parent NS delegation and verify that public resolvers consistently reach the PROD name servers.
- Give DT the DS record generated by the PROD zone's key-signing key.
- Ask DT to publish or replace the DS record in the parent `sf.gov` zone.
- If a DS record for the old zone already exists, coordinate its replacement carefully. A parent DS record for the old DEV zone combined with delegation to the new PROD zone can cause DNSSEC-validating resolvers to reject the domain.
- Do not disable or delete an old signing key or hosted zone while the parent zone still references its DS record.

### 7. Validate both environments independently

- Verify that `dev.goodneighborsf.org` resolves through the DEV zone's authoritative name servers and reaches only the DEV CloudFront distribution.
- Verify that `goodneighbor.sf.gov` resolves through the PROD zone's authoritative name servers and reaches only the PROD CloudFront distribution.
- Validate NS, SOA, A, AAAA, CAA, ACM certificate chain, HTTPS behavior, DNSSEC, CloudFront aliases, WAF association, security headers, and application/API behavior.
- Verify the owning AWS account IDs for the hosted zones, certificates, CloudFront distributions, WAF resources, logs, and application resources.
- Test through multiple public recursive resolvers after the applicable TTLs have expired.
- Confirm that no production DNS record points to a DEV application resource.

### 8. Retire the old DEV production zone only after the cutover is proven

- Keep the old DEV-owned `goodneighbor.sf.gov` zone available during a defined rollback window.
- After NS and DS propagation is complete, production has remained stable, and rollback is no longer required, remove the stale production zone and related obsolete certificates or DNS resources from DEV through reviewed Terraform changes.
- Do not remove or alter the DEV-owned `dev.goodneighborsf.org` hosted zone.
- Preserve the old zone's record inventory and cutover evidence with the change record.

### 9. Close remaining account-isolation gaps

- Give DEV and PROD distinct deployment roles, GitHub Environments, account-ID checks, Terraform state keys, secrets, certificates, logs, and application resources.
- Review the shared Terraform backend. The repository currently documents both state files in a bucket owned by DEV account `518892333858`. If "fully isolated" includes the infrastructure control plane, migrate PROD state to a PROD-owned, versioned, encrypted state bucket and PROD-owned lock table using a separately reviewed state-migration procedure.
- Review the PROD Terraform dependency on DEV remote state for the `dev.goodneighborsf.org` delegation and DEV SES DKIM tokens. For strict isolation, replace direct PROD reads of DEV state with an explicit DNS handoff, stable configuration input, or separately governed shared-DNS layer.
- Ensure PROD deployment permissions cannot mutate DEV resources and DEV deployment permissions cannot mutate PROD resources.

## Cutover sequencing summary

1. Inventory the existing zones, records, delegation, and DNSSEC state.
2. Confirm that `dev.goodneighborsf.org` remains healthy and DEV-owned.
3. Provision and populate the new `goodneighbor.sf.gov` zone in PROD.
4. Validate the PROD CloudFront alias and certificate readiness.
5. Have DT replace the parent NS delegation with the PROD name servers.
6. Verify delegation, then have DT publish or replace the PROD DS record.
7. Validate both domains and their AWS-account ownership.
8. Observe the rollback window, then retire only the obsolete DEV production resources.
9. Resolve shared-state and cross-environment Terraform dependencies if strict control-plane isolation is required.

## Completion criteria

- `dev.goodneighborsf.org` is authoritative in and served entirely from the DEV AWS account.
- `goodneighbor.sf.gov` is authoritative in and served entirely from the PROD AWS account.
- The parent `sf.gov` NS records contain the PROD zone's four name servers.
- The parent `sf.gov` DS record matches the active PROD key-signing key.
- DNSSEC validation succeeds publicly for `goodneighbor.sf.gov`.
- DEV and PROD CI roles are account-scoped and cannot deploy across the environment boundary.
- No production DNS, certificate, CloudFront, WAF, logging, secret, or application dependency remains in DEV, except any explicitly approved shared service.
- Any accepted cross-account dependency, including Terraform state or shared DNS administration, is documented and approved as an exception to full isolation.
